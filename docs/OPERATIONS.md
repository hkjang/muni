# 운영 안내

백업, 복구, 마스터 키 관리. 사고가 난 뒤에 읽으면 늦는 문서입니다.

## 무엇을 지켜야 하는가

muni의 상태는 **두 가지**뿐입니다.

| | 무엇 | 잃으면 |
| --- | --- | --- |
| 데이터베이스 | 문서, 버전, 댓글, 첨부, 설정, 감사 로그 | 전부 |
| `ENCRYPTION_KEY` | 비밀값을 봉인한 master key | 아래 참조 |

이미지에는 상태가 없습니다. 컨테이너는 언제든 버리고 다시 만들어도 됩니다.

**첨부 파일도 데이터베이스 안에 있습니다.** 별도로 백업할 파일 디렉터리가 없는 대신, 데이터베이스 백업이 첨부까지 포함하며 그만큼 커집니다.

## ENCRYPTION_KEY를 잃으면

이 키는 다음을 봉인합니다.

- 서비스 설정의 비밀값 — AI API key, OIDC client secret, SMTP 비밀번호, Ptium API key
- 사용자별 data key (`user_keys.wrapped_key`)

**복구 수단은 없습니다.** 봉인된 값은 이 키로만 열립니다. 백업된 데이터베이스가 있어도, 키가 없으면 그 안의 비밀값은 열 수 없습니다.

키를 잃었을 때 할 수 있는 일은 **다시 설정하는 것**뿐입니다.

1. 새 키를 만들어 `ENCRYPTION_KEY`에 넣고 기동합니다.
2. `서비스 관리 → 서비스 설정`에서 AI, OIDC, SMTP, 발표자료 연동의 비밀값을 **다시 입력**합니다.
3. 사용자 개인 키는 `사용자 관리 → 키 관리`에서 회전시킵니다.

문서 본문은 봉인 대상이 아니므로 그대로 남습니다.

> 키는 데이터베이스 백업과 **다른 곳**에 보관하세요. 같은 곳에 두면 하나를 잃을 때 둘 다 잃습니다.

## 백업

### 정기 백업

```bash
docker compose exec -T postgres \
  pg_dump -U muni -d muni --format=custom --compress=9 \
  > muni-$(date +%Y%m%d).dump
```

`--format=custom`은 선택적 복원을 가능하게 하고 압축이 들어갑니다.

키는 따로 보관합니다. 예를 들어:

```bash
grep '^ENCRYPTION_KEY=' .env > muni-key-$(date +%Y%m%d).txt
chmod 600 muni-key-*.txt
```

### 백업이 실제로 복원되는지 확인

**복원해 본 적 없는 백업은 백업이 아닙니다.** 분기에 한 번은 다른 데이터베이스에 실제로 복원해 보세요.

```bash
createdb -U postgres muni_restore_test
pg_restore -U postgres -d muni_restore_test --no-owner muni-20260101.dump
psql -U postgres -d muni_restore_test -c "SELECT count(*) FROM documents;"
dropdb -U postgres muni_restore_test
```

### 백업 크기 줄이기

첨부가 데이터베이스에 들어 있어 백업이 커집니다. `서비스 관리 → 보존 정책`에서 휴지통과 오래된 버전을 정리하면 크기가 줄어듭니다. 정리는 되돌릴 수 없으니, **켜기 전에 미리보기로 규모를 확인**하세요.

## 복구

```bash
docker compose down
docker volume rm muni_postgres_data      # 볼륨 이름은 설치에 따라 다릅니다
docker compose up -d postgres
docker compose exec -T postgres pg_restore -U muni -d muni --clean --if-exists < muni-20260101.dump
docker compose up -d
```

복원한 데이터베이스와 **같은 시점의 `ENCRYPTION_KEY`**를 사용해야 합니다. 키가 다르면 서비스는 기동하지만 비밀값을 열지 못합니다.

기동할 때 마이그레이션이 자동으로 적용되므로, 백업보다 새로운 버전의 이미지로 복원해도 됩니다. 반대 방향(구버전 이미지로 신버전 데이터 복원)은 지원하지 않습니다.

## 마스터 키 교체

정기 교체나 유출 대응으로 키를 바꾸려면, 현재 키로 열 수 있는 동안 값을 **다시 입력**하는 방식으로 합니다.

1. 현재 설정값을 확인해 둡니다(AI, OIDC, SMTP, 발표자료 연동).
2. 새 키로 `ENCRYPTION_KEY`를 바꾸고 재기동합니다.
3. 비밀값을 다시 입력합니다.
4. `사용자 관리 → 키 관리`에서 개인 키를 회전시킵니다.

봉인된 값을 옛 키로 열어 새 키로 다시 봉인하는 자동 절차는 아직 없습니다. 필요하면 위 순서가 그 일을 대신합니다.

## 사고 시 확인 순서

| 증상 | 먼저 볼 곳 |
| --- | --- |
| 기동하지 않음 | `docker compose logs muni` — 마이그레이션 실패인지 DB 연결 실패인지 |
| 로그인은 되는데 AI·메일이 안 됨 | `서비스 관리 → 운영 현황`의 연결 상태 |
| 특정 문서만 열리지 않음 | `서비스 관리 → 문서 관리`에서 소유자와 휴지통 여부 |
| 디스크가 찬다 | 보존 정책, 그리고 `SELECT pg_size_pretty(pg_total_relation_size('attachments'));` |
| 누가 무엇을 했는지 | `서비스 관리 → 감사 로그`, CSV로 내려받기 |
| 이 문서를 누가 볼 수 있나 | `서비스 관리 → 문서 관리 → 권한 보기` |
| 결재가 며칠째 안 넘어감 | 결재자가 퇴사했는지 — 아래 「퇴사자 정리」 |
| 느려졌다는 말이 나옴 | Prometheus를 쓰신다면 `muni_http_request_duration_seconds`의 p95 — 아래 「지표 수집」 |

## 계정 만들기

`서비스 관리 → 사용자 관리 → 계정 만들기`입니다. 한 명씩 만들거나 CSV로 한꺼번에 가져올 수 있습니다.

비밀번호를 비워 두면 muni가 만들어 **그 화면에서 한 번만** 보여줍니다. 해시로만 보관하므로 나중에 다시 꺼낼 수 없습니다 — 잃어버리면 새로 설정하면 됩니다. SMTP를 설정해 두셨다면 「접속 정보를 메일로 보내기」를 켜서 본인에게 바로 보낼 수 있습니다.

**남이 정한 비밀번호로는 로그인만 됩니다.** 받은 사람이 바꾸기 전까지 그 계정이 할 수 있는 일은 자기 정보 확인·비밀번호 변경·로그아웃뿐입니다. 브라우저가 아니라 서버에서 막으므로 API로 우회할 수 없습니다. 관리자가 비밀번호를 재설정한 경우도 같습니다 — 그 값은 관리자가 알고 있으니까요. 사용자 목록에서 「임시 비밀번호」 표시가 붙은 계정이 아직 바꾸지 않은 사람입니다.

CSV는 첫 줄에 열 이름을 넣습니다. `email`만 필수이고 `username`·`displayName`·`role`은 있으면 씁니다. 한글 열 이름(`이메일`·`이름`·`역할`)도 받습니다.

```csv
이름,email,역할
김민수,minsu@example.com,USER
이서연,seoyeon@example.com,ADMIN
```

- 한 행이 잘못돼도 **나머지는 그대로 만들어집니다.** 실패한 행은 줄 번호와 이유가 함께 돌아옵니다.
- 아이디를 비우면 이메일 앞부분을 씁니다. 이미 쓰는 아이디면 뒤에 숫자가 붙습니다(`kimminsu`, `kimminsu-2`).
- 한 번에 500행까지, 파일은 2MB까지.
- 결과 화면에서 임시 비밀번호를 CSV로 내려받을 수 있습니다. **닫으면 다시 볼 수 없습니다.**

OIDC를 쓰신다면 이 화면이 필요 없을 수도 있습니다 — `autoProvision`을 켜면 처음 로그인하는 사람의 계정이 자동으로 만들어집니다.

## 퇴사자 정리

`서비스 관리 → 사용자 관리 → 정리`입니다. 누르면 **그 사람이 지금 무엇을 쥐고 있는지** 먼저 보여줍니다 — 문서, 소유한 공유 워크스페이스, API 키, 열린 세션, 그리고 **그 사람 차례에서 멈춰 있는 결재**.

마지막 항목이 가장 중요합니다. 결재선은 차례가 된 사람만 처리할 수 있으므로, 결재 대기 중인 사람의 계정을 그냥 정지하면 **그 문서들은 영영 진행되지 않습니다.** 정지가 문제를 해결하는 게 아니라 만듭니다.

인계받을 사람을 고르면 한 트랜잭션에서 전부 처리합니다. 도중에 실패하면 아무것도 바뀌지 않습니다 — 문서만 넘어가고 세션은 남은 절반짜리 정리가 가장 곤란하기 때문입니다.

- 문서를 넘기면서 인계받는 사람을 **그 문서가 있는 워크스페이스에 넣습니다.** 찾을 수 없는 문서를 소유하는 것은 소유가 아닙니다.
- **개인 워크스페이스는 넘기지 않습니다.** 그 사람 이름이 붙어 있고, 남에게 주면 사칭처럼 읽힙니다. 안에 있던 문서는 넘어갑니다.
- 결재 차례는 인계받는 사람에게 넘어갑니다. 그 사람이 **이미 같은 결재선에 있으면** 한 명이 두 번 결재하게 되므로 해당 단계를 건너뜁니다.
- 건너뛴 결과 **결재선에 남은 사람이 아무도 없으면 그 요청은 취소되고 문서는 기안 상태로 돌아갑니다.** 승인하지 않습니다 — 결재자가 사라진 것은 승인이 아니고, muni가 스스로 결재를 내리는 일은 없어야 합니다. 작성자가 새 결재선으로 다시 올리면 됩니다.

### 계정은 지우지 않습니다

정지까지가 전부입니다. 감사 로그·결재 기록·문서 이력이 전부 이 계정을 가리키고 있고, 스키마도 그 참조를 `ON DELETE` 없이 두고 있습니다. 의도한 것입니다 — 지우면 "누가 했는지"가 사라지거나, 더 나쁘게는 다른 사람을 가리키게 됩니다.

정지된 계정은 로그인할 수 없고 세션도 끊깁니다. 실질적으로는 없는 계정이고, 기록만 남습니다.

## 누가 이 문서를 볼 수 있나

`서비스 관리 → 문서 관리 → 권한 보기`입니다.

감사 로그는 **누가 열었는지**를 이미 완전하게 기록합니다(`READ_DOCUMENT`·`EXPORT_DOCUMENT`·`DOWNLOAD_ATTACHMENT`). 그런데 감사가 시작할 때 던지는 질문은 보통 반대쪽입니다 — "지금 이 문서를 누가 열 수 있나". 그 답은 소유자·직접 공유·워크스페이스 구성원·공개 범위 네 가지가 우선순위 규칙으로 합쳐진 결과라서, 지금까지는 코드를 읽고 손으로 계산해야 했습니다.

- **한 사람은 한 줄입니다.** 소유자이면서 읽기 권한도 받은 사람은 소유자로만 나옵니다 — 실제로 적용되는 것이 그것이기 때문입니다.
- **기간이 지난 공유는 나오지 않습니다.** 만료된 권한은 권한이 아닙니다.
- **서비스 관리자는 세어서 보여주고 목록에는 넣지 않습니다.** 관리자는 모든 문서를 열 수 있으므로, 문서마다 이름을 넣으면 모든 문서가 과도하게 공유된 것처럼 보입니다. 문서의 성질이 아니라 역할의 성질입니다.
- **정지된 계정에 권한이 남아 있으면 알려 줍니다.** 계정이 다시 열리면 그대로 접근합니다.

### 공개 링크

문서 소유자는 `공유 → 공개 링크 → 링크 만들기`로 **계정 없는 사람도 읽을 수 있는** 주소를 만들 수 있습니다. 관리자 설정의 「공개 링크 공유 허용」이 꺼져 있으면 만들 수도 없고, **이미 만들어진 링크도 열리지 않습니다** — 새 링크만 막는 스위치는 문서가 잘못 나갔을 때 관리자가 찾는 스위치가 아닙니다.

- **읽기 전용입니다.** 익명 편집자가 만든 변경은 누구에게 귀속시킬 방법이 없습니다.
- 주소는 **만든 직후 한 번만** 보입니다. muni는 해시로만 보관하므로 나중에 다시 꺼낼 수 없습니다. 잃어버리면 해지하고 새로 만드세요.
- 비밀번호(4자 이상), 만료 시각, 열람 횟수 제한을 걸 수 있습니다. 횟수 제한은 세는 것과 막는 것이 한 문장에서 일어나므로, 마지막 한 번을 두 사람이 동시에 쓸 수 없습니다.
- 잘못된 주소와 없는 주소는 **똑같이 404**입니다. 앞부분이 맞았다는 사실도 알려주지 않습니다.
- 해지해도 기록은 남습니다. 그 문서가 밖으로 나갔고 몇 번 열렸는지가 그 행의 내용입니다.
- 열람은 감사 로그에 `VIEW_DOCUMENT_LINK`로 남습니다. 로그인한 사람이 없으므로 행위자는 비어 있고 접속 주소가 기록됩니다.

공유되는 것은 **문서뿐입니다.** 워크스페이스 이름도, 소유자도, 다른 문서도 이 경로로 나가지 않습니다.

`서비스 관리 → 문서 관리 → 권한 보기`가 살아 있는 링크를 함께 보여줍니다 — 링크를 빼놓으면 "누가 열 수 있나"라는 질문에 이름을 아는 사람만 답하는 셈이 됩니다.

## 각주

편집기 툴바의 각주 버튼으로 답니다. 주석의 글자는 그것이 붙는 문장 안에 살기 때문에, 문장을 옮기면 주석이 따라옵니다. **번호는 저장하지 않습니다** — 각주의 번호는 다른 각주들 사이에서의 위치이고, 저장해 두면 문단이 움직이는 순간 틀립니다. 내보낼 때 세어서 붙입니다.

형식마다 표현이 다릅니다.

| 형식 | 각주가 놓이는 곳 |
| --- | --- |
| **Word(.docx)** | **페이지 하단.** 워드의 진짜 각주입니다 |
| PDF | 문서 끝, 구분선 아래 |
| HTML | 문서 끝, 본문과 오가는 링크 포함 |
| Markdown | `[^1]` 참조와 문서 끝의 정의 |
| 텍스트 | `[1]` 표시와 끝의 「주석」 목록 |

**PDF에서 페이지 하단에 오지 않는 이유**는 muni가 PDF를 만드는 방식 때문입니다. muni는 HTML을 브라우저로 인쇄해 PDF를 만드는데, 그 브라우저는 주석을 참조가 놓인 페이지에 배치하는 CSS를 구현하지 않습니다. 페이지 하단이 꼭 필요한 문서라면 **Word로 내보내십시오** — 그쪽은 워드가 직접 배치합니다.

편집기 화면에서는 각주가 괄호처럼 문장 안에 보입니다. 편집기에는 페이지가 없어 하단에 둘 자리가 없고, 아무 데도 닿지 않는 번호는 글자 자체보다 못합니다.

## 지표 수집

Prometheus를 쓰신다면 `GET /metrics`를 긁으면 됩니다. 쓰지 않으신다면 이 절은 건너뛰셔도 됩니다 — 아무것도 설정하지 않아도 muni는 동작합니다.

이 엔드포인트는 **관리자 인증을 요구합니다.** 지표에는 사용자 수와 문서 수가 들어 있어 열어둘 이유가 없습니다. `서비스 관리 → API 키`에서 `api:read` 권한의 키를 하나 만들어 쓰십시오.

```yaml
scrape_configs:
  - job_name: muni
    metrics_path: /metrics
    static_configs:
      - targets: ["muni:8080"]
    authorization:
      credentials: "muni_xxxxxxxxxxxx_..."   # 관리자 계정의 API 키
```

무엇을 볼 수 있는지:

| 지표 | 뜻 |
| --- | --- |
| `muni_http_requests_total{method,status}` | 처리한 요청 수. `status`는 `2xx`·`4xx`·`5xx`처럼 묶여 있습니다 |
| `muni_http_request_duration_seconds` | 응답 시간 히스토그램. `histogram_quantile`로 p95를 뽑으십시오 |
| `muni_documents` / `muni_documents_trashed` | 문서 수 |
| `muni_users` / `muni_users_active` | 계정 수와 정지되지 않은 계정 수 |
| `muni_sessions_open` | 만료되지 않은 세션 |
| `muni_collab_documents_open` / `muni_collab_connections` | 지금 편집 중인 문서와 연결 수 |
| `muni_approvals_pending` | 결재 대기 |
| `muni_attachment_bytes` | 첨부가 차지하는 용량 |
| `muni_notifications_unsent` | 발송되지 않고 남은 알림 — 계속 늘면 SMTP 설정을 보십시오 |
| `muni_ai_calls_last_24h` / `muni_ai_failures_last_24h` | 하루치 AI 호출과 그중 실패 |
| `muni_pdf_renders_in_progress` / `muni_pdf_renders_limit` | 앞의 값이 뒤에 붙어 있으면 PDF 내보내기가 줄을 서고 있다는 뜻입니다 |
| `muni_goroutines`, `muni_memory_bytes` | 프로세스 상태 |

라벨은 메서드와 상태 계열까지만 붙입니다. 문서 ID나 사용자별로 나누지 않는 것은 의도한 것입니다 — 그렇게 하면 문서가 늘어나는 만큼 시계열이 늘어나 Prometheus 쪽이 먼저 무너집니다.

수를 세는 지표들은 **30초 동안 캐시됩니다.** 여러 대가 동시에 긁어도 DB에 `count(*)`가 몰리지 않습니다. 그래서 스크레이프 간격을 30초보다 촘촘하게 잡아도 값은 더 자주 바뀌지 않습니다.

경보를 하나만 건다면 이것을 권합니다:

```yaml
- alert: MuniMailStuck
  expr: muni_notifications_unsent > 50
  for: 15m
  annotations:
    summary: "알림이 발송되지 않고 쌓이고 있습니다 (SMTP 설정 확인)"
```

## 알아두면 좋은 것

- **PDF 내보내기**는 컨테이너 안의 Chromium을 씁니다. 동시 실행 수는 `MUNI_PDF_CONCURRENCY`로 제한합니다(기본 2).
- **협업 상태**(`collab_updates`)는 편집 중에만 쌓이고, 문서를 여는 클라이언트가 주기적으로 하나로 접습니다.
- **감사 로그와 AI 호출 기록**은 보존 정책을 설정하기 전까지 무한히 쌓입니다.
- **메일**은 관리자가 지정한 SMTP 서버로만 나갑니다. 지정하지 않으면 아무것도 발송되지 않습니다.

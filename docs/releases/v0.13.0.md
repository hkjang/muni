관리자가 계정을 만들 수 있게 되었습니다. 이전까지는 만들 방법이 없었습니다 — OIDC를 쓰지 않는 사내 설치에서 muni의 계정은 영원히 하나였습니다. 여기에 퇴사자 정리, 쓸 만해진 사용자 목록, 그리고 "지금 이 문서를 누가 볼 수 있나"에 답하는 화면이 더해졌습니다.

## 추가

### 계정 만들기

`INSERT INTO users`가 muni 코드 전체에서 두 곳뿐이었습니다. 부팅할 때 만드는 관리자 한 명, 그리고 OIDC 첫 로그인의 자동 생성. **OIDC를 쓰지 않는 조직에서는 계정이 하나이고 두 번째 직원이 로그인할 방법이 없었습니다.** 설정에 있는 `allowLocalLogin`은 켜져 있어도 의미가 없었습니다 — 만들 수 있는 로컬 계정이 없었으니까요. 오프라인 사내 설치가 muni의 전제인데, 그 전제에서 쓸 수 없는 상태였습니다.

`서비스 관리 → 사용자 관리 → 계정 만들기`에서 한 명씩, 또는 CSV로 한꺼번에.

비밀번호를 비워 두면 muni가 만들어 **그 화면에서 한 번만** 보여줍니다. 해시로만 보관하므로 나중에 다시 꺼낼 수 없습니다. 읽기 어려운 글자(`O`/`0`, `l`/`1`/`I`)를 빼고 네 글자씩 끊어서 만듭니다 — 한 화면에서 읽어 다른 기계에 입력하거나, 책상 너머로 불러 주는 물건이기 때문입니다. SMTP를 설정해 두셨다면 본인에게 바로 보낼 수 있습니다.

**남이 정한 비밀번호는 아직 비밀번호가 아닙니다.** 받은 사람이 바꾸기 전까지 그 계정이 할 수 있는 일은 자기 정보 확인·비밀번호 변경·로그아웃뿐입니다. 브라우저가 아니라 서버에서 막습니다 — 계정이 메일로 건네지는 이상 API로 우회하는 쪽이 실제 문제입니다. 관리자가 비밀번호를 재설정한 경우도 같습니다. 그 값은 관리자가 알고 있으니까요.

CSV는 첫 줄에 열 이름을 넣고 `email`만 필수입니다. 한글 열 이름(`이메일`·`이름`·`역할`)과 엑셀이 붙이는 BOM도 받습니다. **한 행이 잘못돼도 나머지는 그대로 만들어집니다** — 서른한 번째에 오타가 있다고 마흔 건을 거부하는 것은 아무에게도 도움이 되지 않고, 조용히 건너뛰는 것은 더 나쁩니다. 실패한 행은 줄 번호와 이유가 함께 돌아옵니다.

### 퇴사자 정리

사람이 나가도 그 사람이 가진 것은 남습니다. muni는 문서를 한 건씩, 워크스페이스를 따로, 세션을 또 따로 넘길 수 있었습니다 — 화면 세 곳에서, 무엇이 남았는지 보여주는 목록 없이. "김부장 정리 끝났나?"에 대한 정직한 답은 아무도 모른다는 것이었습니다.

가장 날카로운 부분은 **결재**였습니다. 결재선은 차례가 된 사람만 처리할 수 있으므로, 결재 대기 중인 사람이 나가면 그 단계에서 멈춘 문서는 영영 진행되지 않습니다. 아무 화면도 그것을 보여주지 않았고, **계정을 정지하면 나아지는 게 아니라 나빠졌습니다.**

이제 `정리`를 누르면 그 사람이 지금 무엇을 쥐고 있는지 먼저 보여줍니다 — 문서, 소유한 공유 워크스페이스, API 키, 열린 세션, 그리고 막고 있는 결재 건수. 인계받을 사람을 고르면 **한 트랜잭션에서** 전부 넘어갑니다. 도중에 실패하면 아무것도 바뀌지 않습니다. 문서만 넘어가고 세션은 남는 절반짜리 정리가 가장 곤란하기 때문입니다.

- 문서를 넘기면서 인계받는 사람을 **그 문서가 있는 워크스페이스에 넣습니다.** 찾을 수 없는 문서를 소유하는 것은 소유가 아닙니다.
- **개인 워크스페이스는 넘기지 않습니다.** 그 사람 이름이 붙어 있고, 남에게 주면 사칭처럼 읽힙니다. 안의 문서는 넘어갑니다.
- 인계받는 사람이 **이미 같은 결재선에 있으면** 그 단계를 옮기는 대신 건너뜁니다. 한 사람이 같은 문서를 두 위치에서 결재하게 되니까요.
- 그래서 **결재선이 비면 그 요청은 취소되고 문서는 기안 상태로 돌아갑니다. 승인하지 않습니다.** 결재자가 사라진 것은 승인이 아니고, muni가 스스로 결재를 내리는 일은 관리 작업에서 절대 나와서는 안 되는 결과입니다. 이것을 처리하지 않았다면 "대기 중인데 대기자가 없는" 요청이 남아, 고치겠다는 교착을 고치면서 다시 만드는 셈이었습니다.

**계정은 지우지 않습니다.** 사용자를 참조하는 거의 모든 테이블이 `ON DELETE` 없이 참조하고, 그것이 옳습니다 — 결재 기록·편집 이력·감사 로그는 그 사람이 한 일의 기록이고, 사람을 지우면 그 기록이 사라지거나 다른 사람을 가리키게 됩니다. 넘기고 정지시키되, 한 일의 기록은 남깁니다.

### 지금 이 문서를 누가 볼 수 있나

감사 로그는 **누가 열었는지**를 이미 완전하게 기록하고 있었습니다. 그런데 감사가 시작할 때 던지는 질문은 보통 반대쪽입니다 — "지금 이 문서를 누가 열 수 있나". 그 답은 소유권·직접 공유·워크스페이스 구성원·공개 범위가 우선순위 규칙으로 합쳐진 결과이고, 그 규칙은 코드 안에만 있었습니다.

`서비스 관리 → 문서 관리 → 권한 보기`.

- **한 사람은 한 줄입니다.** 소유자이면서 읽기 권한도 받은 사람은 소유자로만 나옵니다 — 실제로 적용되는 것이 그것이기 때문입니다.
- **기간이 지난 공유는 나오지 않습니다.**
- **관리자는 세어서 보여주고 목록에는 넣지 않습니다.** 모든 문서를 열 수 있는 것은 문서의 성질이 아니라 역할의 성질이고, 문서마다 이름을 넣으면 모든 문서가 과도하게 공유된 것처럼 보입니다.
- **정지된 계정에 권한이 남아 있으면 알려 줍니다.** 계정이 다시 열리면 그대로 접근합니다.

이 화면은 접근 판정 코드가 적용하는 규칙을 SQL로 다시 구현한 것입니다. 둘이 어긋나면 접근 권한을 잘못 말하는 화면이 되고, 그건 화면이 없느니만 못합니다. 그래서 테스트가 실제 데이터베이스에서 공개 범위 세 가지와 사용자 다섯을 모두 돌며 두 구현의 답을 직접 비교합니다.

### 사용자 목록이 관리자의 질문에 답합니다

`ORDER BY created_at DESC LIMIT 50`이 전부였습니다. 직원이 삼백 명이면 최근 오십 명이 보이고 **두 번째 페이지가 없었습니다.** "3월 이후로 로그인 안 한 사람", "초대했는데 아직 안 온 사람", "관리자가 누구인지"에는 답할 방법이 없었습니다 — 바로 그 질문들을 위한 화면인데도요.

상태·역할·로그인 방식(비밀번호/SSO)·마지막 로그인 경과일·임시 비밀번호 보유로 거르고, 다섯 가지로 정렬하고, 페이지를 넘길 수 있습니다. 한 번도 로그인하지 않은 계정은 경과일과 무관하게 「오래 안 온 사람」에 들어갑니다 — 아무도 쓰지 않은 계정이야말로 이 필터가 찾아야 할 행입니다.

## 수정

### 계정 만들기를 붙이면서 드러난 기존 버그 두 개

**아이디가 겹칠 때의 재시도가 한 번도 성공한 적이 없었습니다.** 아이디가 겹치면 뒤에 숫자를 붙여 다시 넣는 코드가 있는데, PostgreSQL은 실패한 문장 하나로 트랜잭션 전체를 막습니다. 재시도는 언제나 "current transaction is aborted"로 끝났습니다. 지금까지 이 코드를 부르는 것이 OIDC뿐이라, 이메일 앞부분이 겹치는 두 사람이 드물어서 아무도 밟지 않았을 뿐입니다. 각 시도를 savepoint 안에서 돌립니다.

**`normalizeUsername("")`은 빈 문자열이 아니라 자리표시자를 돌려줍니다.** 그래서 "아이디가 비어 있으면 이메일에서 뽑는다"는 대체 경로가 한 번도 실행되지 않았습니다. 이메일만 주고 만든 계정은 전부 같은 아이디를 받게 되고, 두 번째부터 전부 실패합니다.

두 버그 모두 OIDC 경로에도 있었고, 계정 생성 로직을 하나로 합치면서 함께 고쳐졌습니다.

### 공개 범위 `LINK`는 아무것도 하지 않고 있었습니다

`LINK`는 문서 공개 범위의 유효한 값이고, API가 받아들이며, 관리자 설정의 「공개 링크 공유 허용」이 그것을 통제하는 것처럼 보입니다. 그런데 **접근 판정에 `LINK`는 존재하지 않고, 링크로 문서를 여는 라우트도 없습니다.** `LINK`로 설정된 문서는 실제로 「제한됨」과 똑같이 동작합니다.

새어 나가는 쪽이 아니라 다행이지만, 설정한 사람은 무언가를 켰다고 믿게 됩니다. 이번 릴리스에서 링크 공유를 만들지는 않았습니다 — 보안에 민감한 별개의 기능이고, 급하게 얹을 것이 아닙니다. 대신 권한 보기 화면이 그런 문서를 만나면 사실대로 알려 주고, 운영 안내에도 적었습니다.

### 쓰이지 않는 테이블 하나

`ai_sessions`는 AI 대화를 묶는 스레드를 설명하는 테이블이었지만 muni에는 그런 것이 없습니다. 에이전트 패널은 질문 하나에 답 하나입니다. 이 테이블에 행을 넣는 코드가 없어 지금까지 기록된 모든 AI 호출의 `session_id`는 NULL입니다. 스키마를 여는 사람이 외래 키를 보고 AI 사용량이 대화 단위로 묶인다고 결론짓게 되므로 지웠습니다. 삭제는 테이블이 비어 있을 때만 실행합니다.

## 개발 환경

CI가 PostgreSQL 16을 띄우고 통합 테스트를 실행합니다. 네 테이블에 걸친 트랜잭션과 스키마 제약을 검사하는 테스트는 가짜 데이터베이스로는 자기 자신하고만 합의합니다. 데이터베이스가 없으면 테스트는 스스로 건너뛰지만, **CI에서는 건너뛰지 않고 실패합니다** — 서비스가 빠지는 날 아무 말 없이 검사가 멈추는 것을 막습니다.

## 업그레이드

마이그레이션이 두 개 있습니다(`011`, `012`). 기동할 때 자동으로 적용되고 설정 변경은 필요하지 않습니다.

`012`는 `ai_sessions` 테이블과 `ai_actions.session_id` 열을 지웁니다. 테이블이 비어 있을 때만 실행하며, 비어 있지 않으면 그대로 둡니다.

```bash
gzip -dc muni-v0.13.0.tar.gz | docker load
docker compose -f compose.example.yaml --env-file .env up -d
```

## 오프라인 설치

릴리스 asset에는 `muni:v0.13.0` Docker 이미지가 포함되어 있습니다.

```bash
gzip -dc muni-v0.13.0.tar.gz | docker load
docker image inspect muni:v0.13.0

cp .env.example .env
# .env의 네 값을 운영 환경에 맞게 변경합니다.
docker compose -f compose.example.yaml --env-file .env up -d
```

처음 기동하면 `BOOTSTRAP_ADMIN` 계정 하나가 만들어집니다. **이제 그 계정으로 나머지 직원의 계정을 만들 수 있습니다.**

애플리케이션이 반드시 필요로 하는 런타임 환경변수는 다음 네 개입니다.

| 환경변수                   | 설명                                 |
| -------------------------- | ------------------------------------ |
| `POSTGRES_DSN`             | PostgreSQL 접속 문자열               |
| `BOOTSTRAP_ADMIN`          | 최초 관리자 아이디 또는 이메일       |
| `BOOTSTRAP_ADMIN_PASSWORD` | 최초 관리자 비밀번호(12자 이상)      |
| `ENCRYPTION_KEY`           | base64로 인코딩한 32-byte master key |

PDF 변환 동작만 조정하는 선택 환경변수가 두 개 있습니다.

| 환경변수               | 기본값    | 설명                                       |
| ---------------------- | --------- | ------------------------------------------ |
| `MUNI_CHROMIUM_PATH`   | 자동 탐색 | PDF Export에 사용할 headless 브라우저 경로 |
| `MUNI_PDF_CONCURRENCY` | `2`       | 동시에 실행할 Chromium 프로세스 수(1~32)   |
